# ADR 001: Backend-For-Frontend (BFF) Pattern

## Status
Accepted

## Context
ShopSwift serves a web storefront and an admin dashboard. Clients need aggregated data (e.g. cart details + product stock + user profile) in single round-trips to optimize Mobile/Web Latency and Core Web Vitals (LCP, INP). Direct microservice calls from the browser would cause:
1. High round-trip latency on mobile connections (chattiness).
2. Complex CORS configurations across dozens of microservices.
3. Leaking internal microservice schemas directly to the browser.
4. Duplicate authorization logic across frontends.

## Decision
Introduce a `bff-service` behind the `api-gateway`:
- The API Gateway acts as the secure edge ingress, handling TLS, rate limiting, and cookie/JWT session translation.
- `bff-service` acts as an orchestration and composition layer for client applications.
- Storefront and admin endpoints (`/bff/home`, `/bff/cart`, `/bff/admin/dashboard`) aggregate responses from downstream services (`product-service`, `order-service`, `inventory-service`, `user-service`) concurrently using Go goroutines with bounded timeouts.
- Microservices remain decoupled and internal; only the gateway and BFF expose endpoints outward.

## Consequences
- **Positive**: Low frontend chattiness; simplified security perimeter; aggregated responses tailored for UI views; unified error mapping.
- **Negative**: Adds an additional network hop for proxied CRUD calls; BFF requires maintenance when downstream service APIs change.
